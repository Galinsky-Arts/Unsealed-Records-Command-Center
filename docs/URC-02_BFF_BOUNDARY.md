# URC-02 backend-for-frontend trust boundary

The BFF validates RS256 signatures against a server-configured JWK set, exact issuer and audience, a five-minute token lifetime, and a signed per-label grant. It does not accept browser-supplied identity flags or labels. Requests without a matching active grant never reach the engine. Only server-configured report routes are outbound. Redirects and unexpected response labels fail closed. Engine credentials stay in the server process. Large decimal values must be strings in the upstream JSON contract.

Run with Node 20 or newer and `node --test tests/bff-*.test.mjs`. Start with `node src/bff/main.mjs`. Configure BFF_ISSUER, BFF_AUDIENCE, BFF_JWKS_JSON, ENGINE_ORIGIN, ENGINE_TOKEN, BFF_REPORT_ROUTES_JSON, OIDC_AUTHORIZATION_ENDPOINT, OIDC_TOKEN_ENDPOINT, OIDC_REDIRECT_URI, OIDC_CLIENT_ID and BFF_SESSION_KEY_BASE64 on the server. The session key must decode to exactly 32 random bytes. The JWKS must come from the trusted identity issuer and rotate with deployment. Example route configuration: `{"streams":"/v1/labels/{labelId}/reports/streams"}`. Do not enable a route until the upstream Music Operations Engine contract and tenant enforcement are verified. Health is at `/healthz`.

The interactive login uses an OIDC authorization-code exchange with PKCE, state and nonce checks. Sessions are encrypted in `__Host-` HttpOnly/Secure/SameSite cookies and expire with the five-minute ID token. The configured issuer must include signed label grants in its ID token; no browser-supplied claims are trusted. There is no local first-admin bootstrap.

Every report additionally checks current membership before the engine request and again before releasing its response. The default is denial. Production startup requires `BFF_MEMBERSHIP_FILE`, an absolute path to a private regular file (mode 0600) with the following schema. Manage the parent directory through trusted deployment administration. Replace the complete file atomically; never modify it through an unauthenticated or browser-facing endpoint. Do not commit live membership records. Missing, malformed, stale, duplicate, wrong-issuer or symbolic-link files deny access.

```json
{"version":1,"revision":1,"issuer":"https://trusted-issuer.example","issuedAtMs":1800000000000,"validUntilMs":1800000600000,"grants":[{"subject":"issuer_subject","labelId":"label_0001","role":"viewer","active":true,"notBeforeMs":1800000000000,"expiresAtMs":1800000300000}]}
```

The timestamps above are illustrative expired fixtures, not deployable grants. The validity window must be no longer than 24 hours. Refresh it through the trusted control plane before expiry. Bind the subject to the configured issuer's immutable subject identifier. First-admin provisioning is an explicit deployment action: grant only a verified issuer subject and explicitly authorized labels; email addresses and first-login order never confer ownership. Effective access is the intersection of the signed token and current file, with the lower role and earliest expiry. Set `active:false` or remove the grant to revoke it. Each replica must receive the updated file before revocation can be considered global; deployments needing a central membership service must supply an authoritative `checkMembership` adapter instead. No cross-replica consistency is claimed for independent files.

Token and report JSON bodies are consumed with byte limits, strict UTF-8 and cancellation on overflow or timeout. The token limit is 20 KB and report limit is 1 MB; content-length cannot bypass streaming limits. Reports preserve source provenance and decimal strings without relabeling cached or synthetic data. Failed requests expose only a fixed public error and can be retried explicitly; there is no automatic financial/provider operation retry.

`GET /api/session` returns only the authenticated subject, token expiry, and labels with current effective roles/expiry. It never returns a token, nonce, issuer key or Engine credential. This menu projection is informational: every report request performs its own current authorization checks. `POST /auth/logout` requires an Origin matching the configured app origin and clears the browser session cookie; GET and cross-site logout requests are rejected. Logout does not revoke a copied bearer token globally: revoke the trusted membership grant for that purpose. Session cookies must fit within 3800 value bytes; excessive signed claims fail login explicitly. Duplicate session cookies and unsupported JWT critical headers fail closed.

Remaining work includes real issuer/account provisioning, verified upstream domain contracts and source ordering, frontend integration, CI coverage, and deployment smoke tests. The existing GitHub workflows do not run BFF product tests. Local HTTP tests use generated fixture keys and simulated providers; they do not establish live identity or Engine interoperability. Keep PR #7 draft until remaining acceptance is verified.

## Production adaptation (2026-11-15)

The deployed entry point is `scripts/start-production.mjs`, which runs `src/server/app.mjs`. It serves the built dashboard and a same-origin, authenticated `/api/v1/*` read proxy to the actual Music Operations Engine routes the dashboard uses (`summary`, `scopes`, `sources`, `catalog`, `source-health`, `platforms`, platform summaries, distributor rows/reconciliations, attendance). Only allowlisted GET routes and query keys pass; ingest, account, job, audit and other write/administrative routes return 404. The Engine credential (`ENGINE_API_KEY`) is attached server-side only, redirects are refused, and upstream errors are replaced by a fixed `UNAVAILABLE` body with `x-data-provenance: unavailable`. Successful responses carry `x-data-provenance: live` (or `synthetic` if the engine marks data synthetic); the dashboard keeps its distinct live, cached, awaiting-producer and synthetic labels.

OIDC is optional because no issuer account is provisioned yet. When all of `BFF_ISSUER`, `BFF_AUDIENCE`, `BFF_JWKS_JSON`, `OIDC_AUTHORIZATION_ENDPOINT`, `OIDC_TOKEN_ENDPOINT`, `OIDC_CLIENT_ID` and `OIDC_REDIRECT_URI` are set, `/auth/oidc/login` and `/auth/callback` run the PKCE/state/nonce flow above and verify the RS256 ID token with `verifyIdentity`. The resulting session is restricted to the active `labelGrants` in that token: requests must name only those labels, family and unscoped requests are refused, and the scope menu is filtered. A partial OIDC configuration refuses startup.

Until OIDC is provisioned, a single local administrator login is the fallback: `ADMIN_USERNAME` (default `admin`) and `ADMIN_PASSWORD` (minimum 16 characters). The password is held only as an in-memory scrypt digest and compared in constant time. This administrator sees all labels the configured Engine credential can read. `POST /auth/login` and `POST /auth/logout` require an exact same-origin `Origin` header (`APP_ORIGIN`, or the request host). Failed logins are rate limited (5 per client and 20 per account per 15 minutes, `429` with `Retry-After`); with `TRUST_PROXY=1` the client is taken from `True-Client-IP`/`X-Forwarded-For`, and the per-account limit applies regardless of spoofed headers. Sessions are HMAC-SHA256-signed cookies (`__Host-urc_session`, HttpOnly, Secure, SameSite=Lax) keyed by HKDF from `SESSION_SECRET` (minimum 32 characters) and expire after `SESSION_TTL_HOURS` (default 8, max 24; OIDC sessions at most one hour). Rotating `SESSION_SECRET` revokes every session. Responses carry CSP, frame denial, HSTS, nosniff and no-referrer headers.

The original `createBff` label-report server (`src/bff/server.mjs`, `main.mjs`) and the membership-file preflight (`scripts/production-config.mjs`) remain as tested modules for the proposed `/v1/labels/{labelId}/reports/*` Engine contract, which the Engine does not yet expose. Security review of this adaptation is an AI-assisted source review plus the automated tests in `tests/app-server.test.mjs` and `tests/dashboard.test.js`; independent human review remains pending.
